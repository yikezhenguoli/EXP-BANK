# AI HELP 进一步智能化

本版修复了两个具体问题：解析器曾把整段中的首个频率和积分套在全部任务上；确认窗口只列名称，看不见错误规则。现在逐项识别、可编辑预览、补充修正和同名偏好已可用，两个入口共用相同逻辑。

## 当前可用的方法

1. 逐项抽取名称、EXP、周期、跨度、次数和任务集，明确每项／全部规则才共享。
2. 缺省值注明“建议”，冲突值要求用户选择；确认之前不改变账本。
3. 复用已有任务集，同名任务默认跳过；人工修正可选记住。
4. 用独立描述集回归，包含口语、数字、多任务差异、错误与歧义，而非只测界面示例。

规则解析适合常见明确指令。它不能像大模型一样充分理解长段意图、隐含关系、复杂指代，或自动把“准备六级”拆成合理计划。

## 建议的后端模型方案

这是下一阶段架构建议，目前没有创建在线服务或连接模型：

- 页面只向自己的受认证后端发送用户主动提交的描述、当前草稿和必要的任务集名称；完整账本、照片与其他凭据不作为默认上下文。
- 后端调用模型，要求输出固定的任务 JSON Schema，列出缺失信息与待确认问题。结构化输出约束格式；业务含义仍需本地校验，不能把格式正确视为理解正确。
- 对时间、每次／总共积分、次数、任务集和重复任务先消歧。信息不足时询问具体字段，不默认编造计划或直接修改已有任务。
- 结果进入本版相同的可编辑预览，确认后才通过统一保存入口创建；不让模型直接操作 localStorage、积分或删除数据。
- 超时、断网或模型拒绝时保留草稿，回退本地解析。用相同测试描述比较逐字段准确率、整组正确率和需澄清比例。
- 服务端持有模型密钥，并配置访问身份、请求限额与用量记录。模型密钥不放在静态 Pages 或浏览器本地存储里。

本版已经接受经过校验的 {"tasks":[...],"setName":"..."} 草稿，因此未来服务可以复用解析和确认层；在线传输、认证、澄清协议和模型服务仍需实施。

OpenAI 官方文档支持用 Structured Outputs 限制 JSON Schema，并要求标准 API 密钥只在服务器保管。这两项不能保证语义识别百分之百正确：

- [Structured model outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)
- [API authentication](https://developers.openai.com/api/reference/overview)

现有仓库只发布静态 PWA。真正接入时需要一个可运行模型请求的后端及其服务端凭据；前端任务草稿、字段校验和确认流程已在本版准备好。
